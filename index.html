Agents that act on the physical world have to be right, not just plausible.

I design agentic AI systems for industrial and physical environments. Preprint2026

Silent Success

Nine cases where a description of a system was read as evidence about its state

arXiv:2609.30307 [cs.SE]  ·  Independent Research

  • Collected nine cases in which a report about a system was taken as evidence about the system's state, admitting a case only when it added a promotion the set did not already have
  • Widened a blocking quality gate from pass and violation to a three-valued verdict, with unable to determine failing, turning silent passes into real failures
  • Placed each case on two axes: the distance between the description and the state it is read as, and how much of the population the description ever touched
  • Two of the nine are in open source projects the author did not write — vLLM, LiteLLM, and MLflow — with patches open upstream
  • Documents eleven self-recurrences of the same pattern inside tooling built to prevent it, one of which passed a check written for that purpose

Preprint2026

Empty Intersection

Two standard provenance prescriptions, measured against the decisions they were meant to repair

arXiv:2609.30308 [cs.SE]  ·  Independent Research

  • Measured two established remedies, a provenance grade on every row and a single write ingress to enforce it, against a frozen snapshot of 194,620 rows from a production pipeline
  • Three interventions repaired 121,296 rows, raised grade coverage from 36 percent to 98 percent, and left the ingress refusing 3,070 writes
  • The two verification decisions the snapshot supports read 32 rows; the repaired rows and the rows those decisions read do not intersect
  • Reports a null result: improving a measured property of a population is not evidence about the correctness of a decision taken over it

05 — FAQ

Frequently asked questions

Tell me about yourself

I build agentic AI systems for physical and industrial environments. My work spans multi-agent orchestration, the data infrastructure those agents reason over, and the embedded hardware at the edge of it — and I am most useful at the seams between them. Most recently I have been designing an agentic digital twin platform for industrial process monitoring, where the interesting problem is not the model but the guarantees around it: data provenance, permission convergence between agents, human approval boundaries, and evaluation that actually fails when it should.

What are your strengths and weaknesses?

My strength is translating AI ideas into working systems by connecting models, data, and deployment. I move comfortably between model development, engineering tradeoffs, and debugging across the stack, and I tend to notice when a system is reporting success without having verified anything. A weakness I continue to work on is spending too long perfecting early solutions; I address it by setting clear milestones, shipping a baseline quickly, and iterating against measurable targets.

Describe a challenging project and how you handled it

On the digital twin platform, the blocking quality gate was passing builds in which zero validations had actually run. Every gate condition was phrased as "did something bad happen?", so absent data answered no and the build went green. I separated "violation" from "unable to determine", derived the expected case count from the case list instead of hardcoding it, and added coverage assertions. The immediate result was a red build, which was the point: that red became the work list, and the final green reflected eight of eight cases actually verified rather than none attempted.

How do you prioritize your work?

By impact, risk, and dependency. I define a minimal baseline first, then iterate with measurable goals. For technical work I front-load the highest-risk components — data correctness, training stability, deployment constraints — so progress stays predictable and results stay reproducible.

How do you work in a team?

I divide responsibilities clearly, communicate progress in short concrete updates, and keep interfaces stable so others can build on my work without waiting on me. I care about aligning on evaluation criteria early, because most team disagreements about direction are really disagreements about what counts as working.

How do you stay current?

I read research papers and practical engineering writeups, reproduce key ideas in small experiments, and apply what survives in real projects. I also track deep learning tooling and deployment practice so I can move from prototype to reliable system without rewriting everything.

2026 – Present  ·  System Architect

Agentic Digital Twin Platform

Industrial Process Monitoring

A layered platform that mirrors a live industrial process in software and lets LLM agents reason over it. Sensor and process data enter through a single validated gateway, a live twin maintains current plant state, anomalies are detected and routed to agents that interpret them and propose operator actions. Every recommendation that could affect plant operation stops for human approval before execution.

Technologies

PythonFastAPILangGraphPostgreSQLTimescaleDBpgvectorApache KafkaDockerCI/CD

Role

  • Designed a six-layer service architecture separating data foundation, digital twin, multi-agent reasoning, and operator-facing views, with an explicit contract at every boundary so each service deploys and is replaced independently
  • Specified a shared event schema carrying a data provenance grade (raw, derived, interpolated), structurally preventing machine learning models from being retrained on estimated values
  • Implemented agent orchestration with approval interrupts that persist to a checkpoint, so an approval-pending workflow survives process restart
  • Defined permission convergence rules for agent-to-agent calls so a low-privilege agent cannot reach a restricted action through a higher-privilege one

Challenges & solutions

  1. The evaluation gate passed when nothing had been evaluated. Zero successful validations still reported a passing build, because every gate condition was phrased as "did something bad happen?" and missing data answered no. I separated "violation" from "unable to determine", derived the expected case count from the case list rather than hardcoding it, and added coverage assertions. A silent pass became 8 of 8 verified runs.
  2. A reproducibility gap hidden for four months. Schema definitions were committed but never applied by any caller; leftover data in the development database masked the absence. Consolidating the seed path made local and CI runs match to fourteen decimal places.
  3. A remote code execution path in a dependency. A third-party checkpoint library permitted arbitrary module import during deserialization under its default configuration. Environment-variable mitigation was ineffective, so the fix was an explicit serializer injected in code.

Outcomes

  • Blocking evaluation gate now distinguishes pass, violation, and undetermined — the third case no longer folds into pass
  • Deterministic baseline reproducible across local and CI environments
  • Provenance grading enforced at the write path, not by convention
  • Contract-first service boundaries enabling independent deployment
